# System Behavior

## Installer

- `drawbore init` — interactive (checkboxes) or flag-driven; installs skills to harness locations, creates `.drawbore/`, appends the Drawbore block to instruction files, and writes `.drawbore-install.json`. Explicit invocation accepts `--no-notebook` and `--no-instruction`, so a caller can install skills only. With no flags on a non-TTY stream it exits 2 and writes nothing. A file where a skill directory belongs is reported as a conflict, and nothing is installed. Running `init` again adds the new locations, instruction files, and skills to the existing install marker instead of replacing them, so one later `uninstall` reverses every accumulated location. The marker records each location's installed skill names in `skillsByLocation` and its selection mode in `skillSelectionByLocation`: `full` for a default install and `subset` for an explicit `--skills` install. Rerunning `init` preserves the original instruction-file ownership recorded in `existedBefore`, so a file Drawbore created from nothing is not reclassified as developer-owned.
- Harness locations use canonical containment before mutation: if a selected location or an existing ancestor resolves outside the project through a symlink or junction, `init` reports the destination and exits 1 without copying or removing content through it.

## Update

- `drawbore update` — refreshes an existing install from the install marker: re-copies the package's skills (preserving locally modified ones), re-applies the instruction block, and refreshes the marker. It never creates a notebook and never prompts for locations. A location whose recorded selection mode is `full` receives every skill in the current package, including skills added since the marker was written; a `subset` location keeps only its recorded skills. A marker without selection metadata keeps its recorded set and is not widened.
- Flags: `--dry-run` (preview), `--check` (drift report; exit 1 when a skill is missing, foreign, a path conflict, or modified relative to the package), `--force` (replace a skill directory owned by another package). Local modifications inside an owned skill are preserved even with `--force`.
- `locations`, `instructions`, recorded skill names, and recorded selection modes are all read from the marker, so all are validated before mutation: `locations` against the supported set, `instructions` against the supported `AGENTS.md`/`CLAUDE.md` set and canonical containment inside the project, skill names against the package's current skill set, and selection modes against supported installed locations with the values `full` or `subset`. Containment is canonical: a path whose existing target or ancestors resolve outside the project is reported and exits 1 before anything is written, so a symlink cannot redirect a write or deletion outside the repository. Harness locations receive the same canonical containment check independently of the marker, so a location already symlinked outside the project cannot redirect a refresh. A marker that cannot be read or parsed is reported as invalid and exits 1; a missing marker is reported as no install.

## Uninstall

- `drawbore uninstall` — reverses an install: removes the skills the install owns, the Drawbore block from each recorded instruction file, and the install marker. It never removes a skill it does not own, and a skill with local modifications is kept whole and reported. The notebook survives unless `--purge` is passed. An instruction file the installer created from nothing is deleted with its block; one the developer already had keeps its content, decided by the `existedBefore` list the marker records at install. A marker without that field keeps the file rather than guessing. When the Drawbore block is the file's only content, removal leaves an empty file for a pre-existing file and deletes a file the installer created. The `.gitignore` note is removed either way. Each harness location is checked for canonical containment before removal, so a location resolving outside the project is reported and left untouched. Malformed selection metadata is rejected before any removal.
- Flags: `--dry-run` (preview), `--purge` (also delete `.drawbore/`).
- An instruction file that carries only one of the two drawbore markers is left untouched and reported. `init` refuses to write such a file rather than adding a second marker pair.
- No install recorded in the project is reported and exits 1, matching `update`. An invalid marker is reported as invalid, not as no install.

## Checker

- `drawbore check` — structural linter over `.drawbore/`; codes E000–E016 (errors), W001–W004 (warnings), S001 (stale); `--json`, `--strict`, `--fix`. The notebook index is required. A decision must use a numeric filename prefix with a kebab-case slug and declare `id`, `status`, `significance`, and `date` front matter plus the Context, Decision, Rationale, Alternatives considered, and Consequences sections. `W003` covers the index map at two depths: top-level artifacts, and the records inside `decisions/` and `work/` once the index links those directories. `--fix` aligns decision IDs to filenames, renumbers duplicate IDs above the highest existing ID so retired IDs are never reused, and updates index links for every renamed record.

## Skills

- Eight portable skills: `brainstorm`, `discover`, `recall`, `frame`, `record`, `review`, `init-project`, `release`. Each carries its own `references/` where it needs one; `record` owns `references/questions.md`, the shared rule that a choice dialog collects every pending decision in one submission with one complete decision per map-lined page, which every skill states in its own words.
- The `brainstorm` skill explores an idea through discussion, materially different alternatives, constructive challenge, and convergence on an agreed direction. It works with or without a Drawbore notebook. Conversational exploratory questions remain conversational, while a choice among options appears in a rendered choice page; each pending choice has its own page, and the developer reviews and submits all pending choices together. Convergence requires an understood objective, an agreed direction, no unresolved material decision that could change that direction, identified non-blocking uncertainties, and a complete handoff. The skill does not create or update a Change Brief; `frame` owns project-specific scope and Change Brief lifecycle.
- The `release` skill treats publication verification as read-only. After the release commit and tag, it reports registry approval, version availability, and provenance without editing tracked files, including `CHANGELOG.md`. A failed live publication requires a new version; a rejected staged version with no live registry version may follow the re-tagging rules.
